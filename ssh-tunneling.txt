1. CORE PRINCIPLES: TUNNELING, REDIRECTION, AND OVERLAYS
-------------------------------------------------------------------------------
 * Redirection vs Tunneling:
   - Redirection (Port Forwarding): Simply maps traffic from one port or address 
     to another. It changes the destination data stream from its original 
     target to an alternative location without encapsulation.
   - Tunneling: The process of encapsulating one network protocol within another. 
     This allows traffic to be transmitted transparently across an incompatible or 
     private intermediary network. Tunneling itself does not inherently 
     provide security; it only defines how packets are wrapped.

 * Tunneling vs Virtual Private Networks (VPNs):
   - VPNs are a practical application of tunneling combined with encryption, 
     authentication, and integrity checking over untrusted networks.
   - VPNs manage user authentication, session management, access control, and 
     obscure the source IP address to make packets appear to originate from the 
     VPN endpoint. While all VPNs rely on tunneling, not all tunnels 
     are VPNs.
   - Example Layers: L2TP can encapsulate entire Layer 2 Ethernet frames to make 
     remote systems function as if physically connected to the same LAN, whereas 
     other VPNs operate strictly at Layer 3 to encapsulate IP packets.

2. THE WAN TRANSITION TUNNELING OVERLAYS (IPv6 / IPv4 INTEROPERABILITY)
-------------------------------------------------------------------------------
 * DUAL STACK INTERFACE
   - Mechanism: Hosts and routers natively run both IPv4 and IPv6 stacks in parallel.
   - Selection: Devices choose the protocol based on DNS results (preferring IPv6).
   - Encapsulation / Conversion: None.

 * 6in4 MANUAL OVERLAY
   - Mechanism: Static manual configuration mapping two explicit public IPv4 endpoints.
   - Encapsulation: Wraps native IPv6 packets inside IPv4 headers using IP Protocol 41.
   - NAT Support: No; Protocol 41 cannot traverse NAT structures easily.

 * 6to4 AUTOMATIC OVERLAY (RFC 3056)
   - Mechanism: Automatic tunneling that uses public IPv4 addresses to dynamically 
     generate a 48-bit IPv6 network prefix via special 6to4 relays.
   - Target Prefix Base: 2002::/16.
   - Embedded Math Stencil: 2002:<IPv4_In_Hexadecimal>::/48.
   - Master Formula Conversion:
     = IPv4 Address: 192.0.2.4 -> Hex: c000:0204 -> IPv6: 2002:c000:0204::1
     = IPv4 Address: 192.168.199.99 -> Hex: c0a8:c763 -> IPv6: 2002:c0a8:c763::
   - NAT Support: No; requires a public IPv4 address.

 * 4in6 OVERLAY
   - Mechanism: Tunnels legacy IPv4 traffic across an IPv6-only core network.
   - Encapsulation: Wraps IPv4 packets inside IPv6 headers using IP Protocol 4.

 * 4to6 TRANSLATION (NAT64 / DNS64)
   - Mechanism: Stateful protocol gateway translation/header rewriting rather 
     than tunneling encapsulation. DNS64 synthesizes AAAA records from A records.
   - Target Well-Known Prefix: 64:ff9b::/96.
   - Embedded Math Stencil: Lower 32 bits of the IPv6 block encode the raw IPv4.
   - Master Formula Conversion: 
     = IPv4: 203.0.113.5 -> Hex: cb00:7105 -> IPv6: 64:ff9b::cb00:7105
   - NAT Support: Yes.

 * TEREDO TUNNELING OVERLAY (RFC 4380)
   - Mechanism: Automatic transition technology enabling client-to-client IPv6 
     connectivity from behind symmetric or strict NAT via Teredo servers/relays.
   - Encapsulation: IPv6 -> UDP -> IPv4 via UDP Destination Port 3544.
   - Target Prefix Base: 2001:0000::/32.
   - Interface ID Bit Layout: [16 bits Flags] + [16 bits Obfuscated UDP Port] + [32 bits Obfuscated Public IPv4].
   - Obfuscation Math: Inverts bits of external UDP port and client public IPv4 (XOR 1).
   - Master Formula Conversion:
     = IPv4: 100.10.1.1 -> IPv6: 2001:0000:640A:0101::
   - NAT Support: Yes (Specifically built for NAT traversal; Linux uses Miredo).

 * ISATAP INTRA-SITE OVERLAY (RFC 5214)
   - Mechanism: Intra-Site Automatic Tunnel Addressing Protocol for routing IPv6 
     inside internal enterprise IPv4 organization networks (Internal use only).
   - Encapsulation: IPv6 inside IPv4 via IP Protocol 41.
   - Link-Local Math Stencil: FE80::/64 Prefix + 0000:5EFE Interface Tag + [IPv4 in Hex format].
   - Master Formula Conversion:
     = IPv4: 192.168.199.99 -> IPv6: FE80:0000:0000:0000:0000:5EFE:c0a8:c763
     = IPv4: 10.1.2.3 -> IPv6: fe80::5efe:0a01:0203
   - NAT Support: No.

 * OVERLAY VULNERABILITIES & FIREWALL EVASION
   - Protocol 41/3544 Bypass: Perimeter firewalls often ignore or fail to inspect 
     IP Protocol 41 or UDP Port 3544 traffic. Attackers exploit this to smuggle 
     unauthorized IPv6 payloads or establish C2 channels past filters.
   - Stack Exploitation: Tunneling exposes hidden host IPv6 stacks, leaving local 
     services vulnerable to ICMPv6 misuse or fragmented header abuse.

3. HISTORICAL EVOLUTION & SYSTEM COMPONENTS OF SSH (RFC 4251)
-------------------------------------------------------------------------------
 * Implementations & Versions:
   - SSH-1 (1995): Developed by Tatu Ylönen to replace unencrypted rlogin, Telnet, 
     FTP, and rsh. Relied on RSA for key exchange and is vulnerable 
     to man-in-the-middle attacks and weak cryptography.
   - SSH-2: Fixed SSH-1 flaws by standardizing Diffie-Hellman/ECDH key exchanges, 
     AES/3DES symmetric encryption, and HMAC integrity checks.
   - OpenSSH: Free open-source alternative derived from OpenBSD (based on SSH 1.2.12).
   - SSH-1.99: Identification string denoting simultaneous compatibility for both protocols.
   - Clients: OpenSSH (Linux/Unix/Windows PowerShell), PuTTY (Windows), Tectia SSH.

 * Architectural Layer Breakdown:
   - SSH-TRANS (Transport Layer): Controls 3-way handshake, protocol version 
     exchanges, server authentication via digital certificates, encryption setup, 
     and integrity checks via HMAC. Operates on TCP port 22 by default.
   - SSH-USERAUTH (User Authentication): Validates the client user identity to 
     the server using passwords, public keys, or host-based systems.
   - SSH-CONNECT (Connection Layer): Multiplexes the single secure transport channel 
     into multiple distinct logical sub-channels (interactive logins, interactive 
     shells, remote execution, and forwarded TCP/IP streams).

 * Key Switchboard Files & Targets:
   - Client Master Config: /etc/ssh/ssh_config  or  ~/.ssh/config
   - Server Daemon Config: /etc/ssh/sshd_config
   - Validated Server Keys: ~/.ssh/known_hosts
   - Component Tokens: User Keys (Asymmetric), Host Keys (Asymmetric), Session Keys 
     (Symmetric), Key Generator (ssh-keygen), Agent (Key storage in memory).

4. THE COVERT CHANNELS IDENTIFICATION SWITCHBOARD
-------------------------------------------------------------------------------
A covert channel transfers information secretively via protocol attributes not 
legitimately designed for communication, bypassing logging and firewalls.

 * COVERT STORAGE CHANNELS
   - Payload Injections: Embedding unauthorized file blocks or explicit shell commands 
     directly within common application payloads (such as DNS query labels or 
     ICMP packet padding spaces).
   - Header Exploitations: Stashing raw bits into unassigned or volatile header fields.
   - Manipulation Targets:
     = IPv4 Headers: Type of Service (ToS/DSCP), IP ID field, Flags, 
       Fragmentation Offset, and Time-To-Live (TTL modification +/- 1).
     = TCP Headers: Reserved Bit fields, Urgent (URG) Pointer field.

 * COVERT TIMING CHANNELS
   - Mechanics: Manipulating the exact time/arrival intervals between consecutive 
     packets. Delays are introduced on the transmitting edge to represent 
     binary values (1s and 0s). High risk of failure over long distances due 
     to processing thresholds, network jitter, and inter-routing variability.

5. PROTOCOL INSPECTION & ANOMALY ANALYSIS CHANNELS
-------------------------------------------------------------------------------
 * HOST CONNECTION AUDIT
   - $ ss -antlp   (Inspect active TCP socket listeners, PIDs, and process names)
   - $ ss -anulp   (Inspect active UDP socket listeners, PIDs, and process names)
   - $ ps -ef      (Trace process parent-child lineage back to its execution source)

 * ICMP COVER-CHANNEL DETECTION
   - Native Baseline: Identical request and reply byte count blocks. Linux pads 
     sequentially with `0123456789abcdef...` and Windows pads with `abcdefghijklmnopqrstuvw...`.
   - Anomalies Checklist:
     = Size: Lopsided conversations where requests differ significantly from replies.
     = Amount: Bursty transmission patterns attempting to balance asymmetric streams.
     = Payloads: Plaintext command phrases or tool strings hidden in packet bytes.
     = Balance: 1 Request generates multiple Replies (indicates TCP over ICMP).
   - Attack Tools Catalog:
     = ptunnel: Fully developed ICMP tool handling concurrent connections and auth.
     = Loki: Venerable 1996 Phrack ICMP backdoor application.
     = 007Shell: Pads packet payloads in strict 64-byte chunks to blend in.
     = ICMP Backdoor: Simple tool using only ping reply packets.
     = B0CK: Implements IGMP multicast messages for covert transmission.
     = Hans: IP-over-ICMP parser employing TUN/TAP devices to bypass drop rule policies.

 * DNS COVER-CHANNEL DETECTION
   - Native Baseline: Query to response patterns resolving strings. Standard UDP 
     payload ceilings: 512 bytes (IPv4) or 1232 bytes (IPv6 with EDNS).
   - Anomalies Checklist:
     = Amount: Mass loop requests targeted at an identical high-level domain structure.
     = Payload: High-entropy base64/hex encryption labels traversing TXT or CNAME records.
     = Balance: Bursting, long-running streams simulating persistent TCP sessions.
   - Attack Tools Catalog:
     = OzymanDNS: Perl client script encoding STDIN values into outbound subdomains.
     = NSTX: Nameserver Transfer Protocol encapsulating total IP packets over queries.
     = dns2tcp: Relays specific TCP traffic structures across targeted DNS channels.
     = DNSCAT2: Encrypted subdomains utilized for stealth command and control routing.

 * HTTP / STEGANOGRAPHY ANALYSIS
   - Baseline: Quick, short burst stateless GET or POST interactions requesting assets.
   - Anomalies Checklist: Persistent, long-running unencrypted keep-alive communication 
     streams, or files running through generation engines to mask structures.
   - Attack Tools Catalog: StegSecret, HyDEn, Spammimic (hides files inside spam text strings).

6. MULTI-TIER PORT FORWARDING & PIVOTING ARCHITECTURE
-------------------------------------------------------------------------------
 * MASTER COMMAND FLAGS
   - `-N`: Do not execute a remote command (Strictly port forward operations).
   - `-T`: Disable pseudo-terminal (pty) allocation.
   - `-f`: Fork SSH execution to background immediately prior to connection.

 * OPENSTACK ROUTING RULES
   - Cross-Environment (Inter-OpenStack): You must target the public "floating" IP.
   - Internal Environment (Intra-OpenStack): Target the private internal IP directly.

 * LOCAL PORT FORWARDING (-L)
   - Master Formula: ssh student@<Hop_IP> -L <Local_Bind_Port>:<Target_Host_IP>:<Target_Port> -NT
   - Single Jump Implementation:
     $ ssh student@172.16.1.15 -L 2280:172.16.40.10:80 -NT
     (Maps local port 2280 to 172.16.40.10 port 80 via 172.16.1.15 pivot)

 * REMOTE (REVERSE) PORT FORWARDING (-R)
   - Master Formula: ssh student@<Remote_Server_IP> -R <Remote_Bind_Port>:<Target_Host_IP>:<Target_Port> -NT
   - Production Implementation:
     $ ssh student@10.10.0.40 -R 5522:172.16.40.10:22 -NT

 * DYNAMIC PORT FORWARDING (-D)
   - Master Formula: ssh student@<Pivot_IP> -D <SOCKS_Proxy_Port> -NT
   - Tool Configuration (/etc/proxychains.conf):
     [ProxyList]
     socks4  127.0.0.1  9050
   - Proxy Execution Blueprint:
     $ ssh student@172.16.1.15 -D 9050 2>/dev/null
     $ proxychains nmap -Pn -sT 172.16.40.0/27 -p 21-23,80

7. STEP-BY-STEP PRODUCTION PIVOT RUNBOOK (TIERS 1 TO 5)
-------------------------------------------------------------------------------
Follow this exact structural layout for pivoting deeply across network tiers using 
nested local port forwards and shifting dynamic SOCKS tunnels:

### PHASE 1: FIRST PIVOT ACQUISITION (Host: John)
1. Gain access and download discovery logs from the initial landing zone:
   internet_host$ scp john@10.50.x.x:/usr/share/cctc/john.png .

### PHASE 2: SECOND PIVOT DISCOVERY (Host: Jack)
1. Establish a local dynamic tunnel to the first pivot point on default proxychains port:
   internet_host$ ssh john@[float ip] -D 9050 2>/dev/null
2. Scan through the proxy to find internal hosts:
   internet_host$ proxychains ./scan.sh
   (Discovered host Jack at 104.16.181.15 with open port 22/SSH)
3. Run target file pulling scripts over web protocols if alternative ports are exposed:
   $ proxychains wget -r http://104.16.181.15:[port]
   $ proxychains curl ftp://104.16.181.15/file
4. Enumerate Jack natively via terminal sessions:
   internet_host$ proxychains ssh jack@104.16.181.15
5. Pull exfiltrated assets back through the dynamic wrapper:
   internet_host$ proxychains scp jack@104.16.181.15:/usr/share/cctc/jack.png .

### PHASE 3: THIRD PIVOT DISCOVERY (Host: Bill)
1. Tear down the old dynamic session to John.
2. Set up a nested local port forward mapping local port 1111 straight to Jack's SSH listener:
   internet_host$ ssh john@[float ip] -L 1111:104.16.181.15:22 -NT
3. Launch a secondary dynamic tunnel directly targeting Jack through that local bind:
   internet_host$ ssh jack@localhost -p 1111 -D 9050 2>/dev/null
4. Run scripts to identify deeper tiers:
   internet_host$ proxychains ./scan.sh
   (Discovered host Bill at 142.16.8.41 with alternate port 4567/SSH)
5. Interrogate and extract data blocks from Bill:
   internet_host$ proxychains ssh bill@142.16.8.41 -p 4567
   internet_host$ proxychains scp -P 4567 bill@142.16.8.41:/usr/share/cctc/bill.png .

### PHASE 4: FOURTH PIVOT DISCOVERY (Host: Brian)
1. Tear down the active dynamic session to Jack.
2. Extend the chain by wrapping port 2222 through Jack straight to Bill's custom listener:
   internet_host$ ssh jack@localhost -p 1111 -L 2222:142.16.8.41:4567 -NT
3. Route a new dynamic SOCKS tunnel through Bill's endpoint:
   internet_host$ ssh bill@localhost -p 2222 -D 9050 2>/dev/null
4. Perform discovery routines:
   internet_host$ proxychains ./scan.sh
   (Discovered host Brian at 155.39.88.21 with legacy port 23/Telnet open)
5. Log into the telnet session securely:
   internet_host$ proxychains telnet 155.39.88.21
   *CRITICAL RULE:* NEVER establish a remote SSH connection from a proxychains telnet session. If you kill your dynamic tunnel, you will lose connection and your remote session will hard drop.

### PHASE 5: FIFTH PIVOT EXTENSION
1. Kill previous dynamic tunnels to establish concrete routing loops.
2. Bind local port 3333 to Brian's Telnet port via Bill:
   internet_host$ ssh bill@localhost -p 2222 -L 3333:155.39.88.21:23 -NT
3. Interconnect across the internal nodes via reverse-forwarding configurations:
   internet_host$ telnet localhost 3333
   brian$ ssh bill@155.39.88.17 -p 4567 -R 4444:localhost:22 -NT
4. Bridge the remaining gaps using localized pipeline switches:
   internet_host$ ssh bill@localhost -p 2222 -L 5555:localhost:4444 -NT
5. Spawn the final operational dynamic session:
   internet_host$ ssh brian@localhost -p 5555 -D 9050 2>/dev/null
   internet_host$ proxychains ./scan.sh

### BONUS CONFIGURATION: HIGH-SPEED MULTI-JUMP TUNNELING (-J)
- Stencil syntax formatting multiple intermediate jump boxes in a single line string command:
  $ ssh -J student@172.16.1.15,student@172.16.40.10 student@172.16.82.106 -L 1111:192.168.1.10:22 -NT
- Connect straight through the established loopback point:
  $ ssh student@localhost -p 1111
